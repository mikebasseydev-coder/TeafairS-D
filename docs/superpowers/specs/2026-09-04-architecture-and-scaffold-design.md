# TEFAIR Architecture & Repo Scaffold — Design Spec

**Date:** 2026-09-04
**Status:** Draft for review
**Companion to:** `2026-09-03-serverless-rtm-platform-design.md` (the platform
spec — data model, RPCs, RLS, features). This spec covers *how the code is
organised and built*; the platform spec governs *what it does*.

---

## 1. Purpose

The platform spec assumes a `pnpm` monorepo with `apps/mobile-android`,
`apps/desktop-windows`, `packages/shared-*`, and `supabase/`. This spec fixes the
framework choices, the package boundaries, the build and local-dev pipelines, and
the migration from the legacy `frontend/` scaffold — so the implementation plans
can be written against a known skeleton.

Nothing here is scaffolded yet. `apps/`, `packages/`, and `supabase/` currently
hold only `CLAUDE.md` files.

## 2. What "scaffolded" means (success criteria)

1. `pnpm install` at the root wires every workspace; `pnpm -w typecheck` and
   `pnpm -w test` pass with the skeleton in place.
2. `apps/mobile-android` runs on a physical Android device via the Expo dev
   client; a smoke path — sign in (MFA), load a cache-backed dashboard, submit
   one RPC — works, including once offline then flushed.
3. `apps/desktop-windows` builds and runs on Windows via `react-native-windows`;
   the same smoke path (minus offline) works.
4. Both apps import `packages/shared-*` and compile against **one** generated
   Supabase type set.
5. `supabase start` brings up the local stack; `supabase db reset` applies every
   migration + seeds all roles; `pnpm gen:types` regenerates
   `packages/shared-types`.
6. `scripts/build-android.sh` produces a signed `build/mobile/Teafair.apk` (via
   EAS); `scripts/build-windows.sh` produces a signed `build/desktop/Teafair.msix`;
   `scripts/deploy-supabase.sh` runs `supabase db push` + `supabase functions
   deploy notify`.
7. CI runs lint + typecheck + unit tests on every PR and blocks on failure.

## 3. Framework decision

| App | Framework | Why |
|---|---|---|
| `apps/mobile-android` | **Expo** (prebuild / CNG) + React Native | OTA updates (EAS Update) to a distributed, growing field + travelling-HQ user base without Play Store round-trips; a maintained, version-matched native-module set (camera, location, secure store, notifications, file system) the field app leans on heavily; EAS Build removes local Android-toolchain setup. |
| `apps/desktop-windows` | **bare React Native + `react-native-windows`** | Expo has no Windows support. The HQ workstation needs none of Expo's mobile conveniences and does need direct MSBuild/MSIX control for signing and enterprise distribution. |

### The version-coordination rule

Expo SDK pins a specific RN version; `react-native-windows` supports RN on its
own (usually lagging) schedule. **Pin RN to the newest version
`react-native-windows` supports, then choose the Expo SDK that targets that same
RN version** (Expo publishes the SDK↔RN mapping). Verify the pairing before
scaffolding. Both apps upgrade together, on `rnw`'s cadence — never bump one
alone.

- `apps/mobile-android`: **CNG** — `android/` is *not* committed; native config
  lives in `app.config.ts` + config plugins, regenerated by `expo prebuild`.
- `apps/desktop-windows`: `windows/` **is** committed (`rnw` is not CNG-friendly).

### `shared-ui` constraint

Components in `packages/shared-ui` may use only `react-native` primitives +
NativeWind — **no Expo modules**, so they compile under both apps. Anything
needing an Expo module (camera preview, image manipulation) lives in
`apps/mobile-android` directly. In practice the field and HQ UIs diverge enough
that `shared-ui` stays small (buttons, inputs, cards, list rows, empty/error
states, the notification centre shell).

## 5. Packages

Every package: pure TypeScript, no platform-conditional code except `shared-ui`
(RN only) and `shared-supabase` (may import `@supabase/supabase-js`). Consumers
import from `@teafair/<pkg>`, never a deep path.

| Package | Purpose | Exports | May import | Must NOT import |
|---|---|---|---|---|
| `shared-types` | the type contract | `Database`, generated table/enum types, hand-written domain types | — | anything |
| `shared-schemas` | runtime validation | one `zod` schema per RPC's args + shared value schemas (money, phone, GPS) | `zod`, `shared-types` | RN, supabase-js |
| `shared-supabase` | the client + write path | `createSupabaseClient(url, key, opts?)`, typed `rpc.<name>(args)` wrappers, `unwrapResult`, error types | `@supabase/supabase-js`, `shared-types`, `shared-schemas` | RN, Expo |
| `shared-sync` | offline | `CacheStore` (persist-backed), `WriteQueue`, delta-sync driver, connectivity gate | `shared-supabase`, a KV interface (injected) | RN, Expo (KV + netinfo are injected by the app) |
| `shared-hooks` | data access for screens | `useQuery`/`useMutation` wrappers per feature, cache invalidation rules | `@tanstack/react-query`, `shared-supabase`, `shared-sync` | RN components |
| `shared-ui` | cross-app UI | `Button`, `Input`, `Card`, `ListRow`, `Badge`, `EmptyState`, `NotificationCentre` shell | `react-native`, `nativewind`, `shared-config` | Expo, navigation, data packages |
| `shared-config` | constants | enums-as-const mirroring the DB enums, deep-link route map, feature flags, tunable client defaults | — | anything |

**Generated types flow:** `supabase gen types typescript --local` →
`packages/shared-types/src/database.types.ts`, committed, regenerated by
`pnpm gen:types` on every schema change. CI fails if it's stale.

## 6. Apps — shared runtime concerns

### Supabase client & session

- Each app creates one client from `shared-supabase`'s factory, reading env in
  the app (`EXPO_PUBLIC_SUPABASE_URL` / `_ANON_KEY` on mobile;
  `react-native-config` on Windows). The anon key is public-safe — RLS is the
  boundary. **The service-role key never appears in an app.**
- Session storage: a keychain-backed adapter injected into the client's
  `auth.storage`. Mobile: `react-native-keychain` (via Expo config plugin) — not
  `expo-secure-store`, whose ~2 KB Android per-value limit is tight for a
  Supabase session. Windows: the Windows credential locker via
  `react-native-keychain`.
- `AppState` wiring for `startAutoRefresh` / `stopAutoRefresh` (carried from the
  legacy scaffold). Auth bootstrap + `onAuthStateChange` listener at the app
  root — the app owns this, not `shared-*`.
- MFA enrolment / challenge screens live in each app's `features/auth`.

### Data layer

- **Server state:** TanStack Query. Query keys are `[feature, scope, params]`.
  Mutations call `shared-supabase` `rpc.*` wrappers and declare their invalidation
  set.
- **Persistence (mobile field roles):** `@tanstack/react-query-persist-client`
  with a persister over `react-native-mmkv`. HQ-mobile and Windows: in-memory
  only.
- **UI-only state:** Zustand — auth session mirror, active filters, wizard step.
  **No Redux.**
- **Connectivity:** `@react-native-community/netinfo` feeds `shared-sync`'s gate.

### Navigation

- React Navigation. `apps/mobile-android`: `bottom-tabs`, the tab set chosen by
  role tier at login (field tabs vs HQ tabs — §8.1 of the platform spec).
  `apps/desktop-windows`: a custom sidebar + stack.
- Deep-link targets from `shared-config`'s route map so `notifications.deep_link`
  resolves in both apps.

### Styling

NativeWind v4, one `tailwind.config.js` per app extending a shared preset in
`shared-config`. `shared-ui` components accept a `className` and **merge** it with
their defaults (carried convention).

### Native modules (mobile)

`expo-camera`, `expo-location`, `expo-image-manipulator` (compress before
upload), `expo-file-system`, `react-native-keychain` (plugin), `react-native-mmkv`
(plugin), `@react-native-community/netinfo`. `expo-notifications` is added with
the push fast-follow. Verification captures are assembled in
`apps/mobile-android/src/features/verification` and handed to `shared-sync` /
`shared-supabase` as a plain bundle.

## 7. `shared-sync` — offline (implements platform spec §3.8)

- `CacheStore` — per-collection persisted store keyed by `[collection, scope]`,
  each tracking a `syncedAt` cursor. Delta pull: `updated_at > cursor` (mutable)
  or `created_at > cursor` (append-only), RLS-scoped, via `shared-supabase`.
- `WriteQueue` — ordered `{ rpcName, args, idempotencyKey, capturedAt }`,
  persisted. Flushes **sequentially** on reconnect. Per item: validation error →
  drop + emit a local notification; transient → retry with backoff; a per-flush
  cap bounds burst load.
- The KV backend and the connectivity signal are **injected** by the app so the
  package stays platform-agnostic and testable with a memory KV.
- Only `apps/mobile-android` field roles instantiate it. HQ-mobile and Windows
  use `shared-hooks` directly against live data.

## 8. `supabase/`

### Local development

- `supabase start` runs the full local stack (Postgres + Auth + Storage + Edge
  runtime + Studio). This uses Docker *locally only* — it is dev tooling, not
  production infra, and mirrors prod exactly. It replaces the deleted
  Prisma/Docker sandbox.
- **Declarative schema** in `supabase/schemas/*.sql` is the source of truth.
  `supabase db diff -f <name>` generates a migration into `supabase/migrations/`;
  `supabase db reset` rebuilds local from migrations + `seeds/seed.sql`.
- Schema files are split by area to match `docs/features/` (e.g.
  `01_roles.sql`, `02_geography.sql`, `03_inventory.sql`, … `12_notifications.sql`).
  RPCs, RLS policies, triggers, and `pg_cron` schedules live alongside their
  tables.

### `functions/notify`

Deno. Drains `notifications_outbox` in batches, sends via the SMS gateway
(credentials in the function's env / Supabase Vault), marks rows `SENT`/`FAILED`.
Invoked by a `pg_cron` job (`select net.http_post(...)` or `supabase functions`
schedule) every minute. This is the **only** Edge Function at launch.

### Seeds

`seeds/seed.sql` creates: one of every role (auth user + profile), 2 zones, 3
warehouses (incl. an informal-rep depot), a product set, a few outlets +
guarantors, one fintech agent (indemnity accepted), and a handful of
orders/movements — enough for every screen to render and every RPC to be
exercised locally.

### Type generation

`scripts/gen-types.sh` → `supabase gen types typescript --local >
packages/shared-types/src/database.types.ts`. Run after every `db diff`.

## 9. Build & distribution

| Target | Tool | Output | Script |
|---|---|---|---|
| Android APK/AAB | **EAS Build** (profiles: `development`, `preview`, `production`); signing via EAS-managed credentials | `build/mobile/Teafair.apk` | `scripts/build-android.sh` |
| Android OTA | **EAS Update** — channel per profile | — | `eas update --channel production` |
| Windows MSIX | MSBuild + the `rnw` toolchain; signed with the org cert | `build/desktop/Teafair.msix` | `scripts/build-windows.sh` |
| Backend | Supabase CLI | — | `scripts/deploy-supabase.sh` → `supabase db push` + `supabase functions deploy notify` |

`scripts/deploy-supabase.sh` also runs `supabase db lint` and refuses to push if
`gen:types` output would change (schema/committed-types drift).

## 10. Tooling

- **TypeScript:** `tsconfig.base.json` at root (`strict`, `noUncheckedIndexedAccess`);
  each package/app extends it. Workspace resolution via `workspace:*` +
  `paths`.
- **Lint/format:** ESLint (flat config) + Prettier. Shared config in a root
  `eslint.config.js`; RN + React Hooks + import-order rules. `pnpm -w lint`.
- **Task runner:** Turborepo — `build`, `lint`, `typecheck`, `test` pipelines with
  caching; `turbo.json` declares the graph.
- **Testing:**
  - `packages/*` — Jest: schema round-trips, `rpc` wrapper argument mapping,
    `shared-sync` queue/cursor logic (memory KV), utils.
  - `shared-ui` / screens — `@testing-library/react-native`.
  - **RPC + RLS** — Node scripts (pg client) or `pgTAP` run against `supabase
    start`; the platform-spec implementation plans are test-first per RPC.
  - `apps/desktop-windows` — `tsc --noEmit` + a minimal RNTL suite + a manual
    smoke checklist (no Windows CI runner assumed at launch).
  - E2E (Maestro, mobile) — post-launch.
- **CI (`.github/workflows/ci.yml`):** on PR — `pnpm install`, `turbo lint
  typecheck test`, `supabase db lint`, types-drift check. `release.yml` on tag —
  EAS Build + `deploy-supabase.sh` (gated on approval).

## 11. Environment & secrets

- `.env.example` committed at root and per app; real `.env` / `.env*.local`
  gitignored (carried convention — never hardcode URLs/keys).
- Mobile: `EXPO_PUBLIC_SUPABASE_URL`, `EXPO_PUBLIC_SUPABASE_ANON_KEY` (inlined by
  Metro; anon key is safe under RLS).
- Windows: `SUPABASE_URL`, `SUPABASE_ANON_KEY` via `react-native-config`.
- `notify` function: SMS gateway credentials + `SUPABASE_SERVICE_ROLE_KEY` in the
  function env / Vault only.
- EAS: secrets via `eas secret`. CI: GitHub Actions secrets.

## 12. Migration from `frontend/`

`frontend/` (npm workspaces: `core` + `mobile` Expo, ~24 commits, 39 passing
tests) is a **greenfield restart**. Concrete steps (become the first
implementation plan):

1. Scaffold the monorepo skeleton (§4) — empty packages, both apps via
   `create-expo` (mobile) and `npx react-native init` + `npx react-native-windows-init`
   (windows), pinned to the coordinated RN version.
2. Port the client factory idea into `shared-supabase`; port `unwrapSupabaseResult`
   into it verbatim (rename `unwrapResult`).
3. Port the `Storage` interface → the injected KV in `shared-sync` + the keychain
   adapter in each app.
4. Port the auth-store shape into each app's `features/auth` (Zustand) + the
   `useAuthBootstrap` pattern.
5. Re-create the auth flow (sign in / sign up / MFA) against the real
   `signInWithEmail` etc. — the one piece of the legacy `core` that had real
   logic.
6. Generate types from a first `supabase db reset`; wire one end-to-end screen
   (a dashboard) through `shared-hooks`.
7. Delete `frontend/`.

The legacy placeholder feature modules, the NativeWind setup, and the bottom-tab
navigator are re-created fresh, not copied.

## 13. Build sequence

1. Monorepo skeleton + tooling (§4, §10) — `pnpm install` green, CI green.
2. `supabase/` local stack + declarative schema for **roles & access** only +
   seeds + type gen (§8).
3. `shared-types`, `shared-config`, `shared-schemas`, `shared-supabase`.
4. `apps/mobile-android`: Expo scaffold, client + session, auth + MFA, one
   dashboard screen. Smoke on a device.
5. `apps/desktop-windows`: `rnw` scaffold, same client + auth, one dashboard.
   Smoke on Windows. **(Do this early — it's the riskiest target.)**
6. `shared-sync` + wire the mobile field cache/queue against the seeded data.
7. `shared-ui`, `shared-hooks` fleshed out; navigation shells for both apps.
8. Then the platform-spec implementation plans, feature by feature, each adding
   its `supabase/schemas` slice + `shared-*` surface + screens in both apps as
   applicable.

## 14. Open questions

1. **RN / Expo SDK versions** — confirm the current `react-native-windows`
   latest-supported RN, and the Expo SDK that matches it, before step 1.
2. **Turborepo** — worth it at 7 packages + 2 apps, or plain `pnpm --filter`
   until build times hurt?
3. **Windows CI** — is a self-hosted Windows runner available for `rnw`
   typecheck/build in CI, or does Windows stay manual-smoke at launch?
4. **OTA policy** — which EAS Update channel maps to which build profile, and
   what's the rollback/staged-rollout policy for field devices?
5. **Cache backend** — `react-native-mmkv` (fast KV, simple) vs `expo-sqlite`
   (queryable, better for large relational caches). MMKV is the default here;
   revisit if the agent cache grows past a few thousand rows.
6. **Windows distribution** — MSIX sideload / intranet share / Microsoft Store
   for Business? Affects the signing cert and `build-windows.sh`.
