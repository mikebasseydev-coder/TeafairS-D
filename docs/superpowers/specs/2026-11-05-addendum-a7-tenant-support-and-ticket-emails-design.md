# Addendum A7 to Spec A: tenant support tickets and ticket emails

Date: 2026-11-05. Status: draft for the user's approval. Built locally only;
nothing is pushed to GitHub or the Supabase remote until asked.

## 1. Why

Two gaps before cloud deployment:

1. **Tenants have no way to raise a problem.** A brand's `TENANT_ADMIN` who
   sees a settlement discrepancy or a stock shortage has no channel inside
   the platform. Their CSM represents them in house (A6 §16), so the
   ticket should land with that CSM first, and with Teafair's central
   `MONVELO_OPERATOR` pool when there is no CSM.
2. **Web buyers never hear back.** A3 §12 left out buyer email ("they
   poll"). A buyer who opens a ticket and waits for an answer has to keep
   checking. This addendum **lifts that exclusion** for email only (SMS
   stays out).

## 2. Decisions (the user's, 2026-11-05)

1. **The buyer email never carries the secret.** It carries the `TK-`
   reference and a ticket-page URL with the reference pre-filled. The
   buyer still types the ticket secret to read messages.
   `support-ticket-read` and its `{ public_reference, secret }` body do
   not change.
2. **Buyer emails fire on three events**: the ticket is opened (a
   confirmation with the reference), a staff member replies, and the
   status changes to RESOLVED or CLOSED. Only when the buyer gave an email.
3. **The ticket link base is a new env var** `WEB_SUPPORT_TICKET_URL`
   (local default `http://localhost:3000/support/ticket`). The sender
   appends `?ref=TK-XXXXXX`.
4. **`TENANT_ADMIN` gets one write exception to A6 §16**: it may open
   support tickets and reply on its own tenant's tickets. Everything else
   stays read only.
5. **Tenant tickets live in their own tables**, not in `support_tickets`.
   The buyer tables, buyer secret and buyer RPCs stay untouched apart from
   the email enqueue (§5.3).
6. **Tenants get email on creation, a Teafair reply, and RESOLVED / CLOSED**
   (the nightly auto-close included), as buyers do.

## 3. Departures from the pasted directive (Claude's, stated to the user)

| Directive | Here | Why |
|---|---|---|
| RLS lets `TENANT_ADMIN` insert | `SECURITY DEFINER` RPC; RLS is `FOR SELECT` only | Spec A §9: no direct client writes |
| `tenant_id` optional on `support_tickets` | own table, `tenant_id NOT NULL` | decision 5; every tenant ticket has a tenant |
| auto-assign to `tenants.csm_id` | there is no such column. A CSM is a `tenant_users` row with role `CLIENT_SERVICE_MANAGER`, and a tenant may have several. Auto-assign only when the tenant has **exactly one** ACTIVE CSM; otherwise null (operator pool) | Claude's call |
| emails fired by `support_ticket_messages` inserts calling an Edge Function | a transactional **email outbox** drained by a cron-invoked system function | staff call `reply_ticket` / `update_ticket_status` straight through PostgREST with no gateway in between; an outbox row commits or rolls back with the write itself, and a Resend outage never fails a reply |
| buyer "secure magic link" | reference plus a pre-filled URL, no secret | decision 1 |

## 4. Tenant support tickets

### 4.1 Tables

`tenant_support_tickets`
- `id uuid PK`; `tenant_id uuid NOT NULL → tenants`; `unique (tenant_id, id)`.
- `public_reference text UNIQUE CHECK (~ '^TS-[0-9A-HJKMNP-TV-Z]{6}$')`,
  generated by the same internal generator as `TK-` / `TF-`. The `TS-`
  prefix is Claude's call: it keeps tenant references distinct from buyer
  ones.
- `category text NOT NULL CHECK in ('TENANT_SETTLEMENT_DISCREPANCY',
  'TENANT_STOCK_SHORTAGE', 'TENANT_ONBOARDING_ISSUE', 'TENANT_GENERAL_INQUIRY')`.
- `subject text NOT NULL` (3–160 characters).
- `opened_by uuid NOT NULL → profiles` (the `TENANT_ADMIN`).
- `assigned_csm_id uuid → profiles`, nullable.
- `status text` OPEN / IN_PROGRESS / RESOLVED / CLOSED, default OPEN;
  `priority text` LOW / MEDIUM / HIGH / URGENT, default MEDIUM (as in A3).
- `last_message_at`, `resolved_at`, `created_at`, `updated_at` (all
  `timestamptz`); `CHECK (status <> 'RESOLVED' or resolved_at is not null)`.

`tenant_support_ticket_messages`
- `id`, `tenant_id`, `ticket_id` with a composite FK `(tenant_id, ticket_id)`.
- `sender_id uuid NOT NULL → profiles`; `sender_side text CHECK in
  ('TENANT', 'TEAFAIR')`; `body text NOT NULL` (1–4000); `created_at`.

Both tables: RLS on, `authenticated` SELECT only, no writes for anyone but
the RPCs.

### 4.2 Who sees what (RLS, `FOR SELECT`)

A row of either table is visible to:
- a live ACTIVE `TENANT_ADMIN` membership of that row's tenant;
- a live ACTIVE `CLIENT_SERVICE_MANAGER` membership of that tenant (every
  CSM of the tenant reads, not only the assigned one: Claude's call, so a
  colleague can cover);
- platform role `MONVELO_OPERATOR`.

Nobody else: other tenants' admins and CSMs, ZSMs, TMs, field roles, the
LOGISTICS_MANAGER and anon all get zero rows. The policies use
`(select auth.uid())` and `public.*` helpers (a new
`public.can_read_tenant_ticket(tenant_id)` stable helper, or an existing
helper if one already fits), never a per-row correlated subquery.

### 4.3 RPCs (`authenticated`, standard write contract)

Every RPC takes `p_idempotency_key uuid` first, re-verifies the role live,
audits, and is `SECURITY DEFINER SET search_path = public, pg_temp`. A
role that may not act gets `42501`. A ticket outside the caller's reach is
`P0002` (not found), so references never leak across tenants.

| RPC | Who | Does |
|---|---|---|
| `open_tenant_ticket(key, p_category, p_subject, p_message)` | `TENANT_ADMIN` | tenant from `jwt_tenant_id()`, verified live against `tenant_users`, never a parameter. Inserts the ticket and the first TENANT message, auto-assigns per §3, notifies (§4.4), enqueues the confirmation email (§5.3). Returns `{ ticket_id, public_reference, status, assigned_csm_id }` |
| `reply_tenant_ticket(key, p_ticket_id, p_body)` | the ticket's tenant's `TENANT_ADMIN`; the assigned CSM; any `MONVELO_OPERATOR` | inserts the message with the caller's side, bumps `last_message_at`. A TEAFAIR reply on OPEN moves the ticket to IN_PROGRESS; a TENANT reply on RESOLVED reopens it to OPEN; CLOSED refuses (`P0001`). A TEAFAIR reply enqueues the reply email to `opened_by` |
| `assign_tenant_ticket(key, p_ticket_id, p_csm_profile_id)` | `MONVELO_OPERATOR` | sets `assigned_csm_id` to a profile that holds an ACTIVE CSM membership of the ticket's tenant (anything else: `P0001`); null returns it to the pool |
| `claim_tenant_ticket(key, p_ticket_id)` | a CSM of the ticket's tenant, only while unassigned | sets `assigned_csm_id` to the caller |
| `update_tenant_ticket_status(key, p_ticket_id, p_status)` | the assigned CSM; `MONVELO_OPERATOR` | the same transitions as A3 `update_ticket_status` (IN_PROGRESS→RESOLVED; OPEN/IN_PROGRESS/RESOLVED→CLOSED) |

**Tenant context (Spec A §9).** A `TENANT_ADMIN` or CSM acts only in the
tenant their JWT names (`jwt_tenant_id()`), re-verified live through
`assert_tenant_role`. A CSM serving several tenants switches tenant to work
another tenant's tickets. A ticket of any other tenant is `P0002`, and the
RLS helper follows the JWT tenant too, not every membership the caller holds.

**An assignee who is no longer ACTIVE counts as unassigned** (Claude's
call). Every check of `assigned_csm_id` re-verifies that profile's ACTIVE
CSM membership in the ticket's tenant live. A suspended CSM cannot reply or
change status, any CSM of the tenant may claim the ticket, and the
"assigned CSM" notifications fall through to the operators.

`release_tenant_ticket(key, p_ticket_id)`: the assigned CSM hands the ticket
back to the pool (`assigned_csm_id` becomes null). Claude's call, so a CSM
is not stuck with a ticket until an operator steps in.

`MONVELO_OPERATOR` is a platform role, so for these RPCs the tenant comes
from the ticket row, not the JWT. Each operator RPC checks the role with
`assert_platform_role`. The tenant's ZSMs are not in this flow (A6 §16:
the CSM represents the tenant).

A CSM that is not assigned may read but not reply. Claude's call: one
voice per ticket, and the CSM claims the ticket first.

Resolved tenant tickets auto-close after 7 days, through the same nightly
pattern as `close_resolved_support_tickets` (extend that function or add a
sibling; builder's call).

### 4.4 In-app notifications

Into the existing `notifications` table, payload `{ ticket_id,
public_reference }` only, no message text (as A3 §5):
- opened, or a TENANT reply → `assigned_csm_id`, else every ACTIVE
  `MONVELO_OPERATOR`; kind `TENANT_TICKET_ACTIVITY`;
- a TEAFAIR reply or a status change → `opened_by`; kind
  `TENANT_TICKET_UPDATE`.

## 5. Ticket emails

### 5.1 The outbox

`email_outbox` (RLS on, no policy, no grant to `anon` / `authenticated`):
- `id uuid PK` (also the Resend `Idempotency-Key`, so a retried send never
  delivers twice);
- `template text CHECK in ('BUYER_TICKET_OPENED', 'BUYER_TICKET_REPLY',
  'BUYER_TICKET_STATUS', 'TENANT_TICKET_OPENED', 'TENANT_TICKET_REPLY', 'TENANT_TICKET_STATUS')`;
- `to_email text NOT NULL` (lower-case);
- `payload jsonb NOT NULL`: only `{ public_reference, status? }` for buyer
  templates, plus `category` and `subject` for tenant ones. **Never a
  message body, never a secret**: the secret is the only gate on a buyer's
  messages, and a body in the email would bypass it;
- `source_table text`, `source_id uuid` (the ticket), so a redaction can
  find its rows;
- `status` PENDING / SENDING / SENT / FAILED; `attempts int`;
  `next_attempt_at`, `sent_at`, `created_at`.

Internal `public.enqueue_email(template, to_email, payload, source_table,
source_id)`: `revoke all from public, anon, authenticated`, called only
from inside the RPCs. A null or empty address enqueues nothing.

### 5.2 The sender

New system Edge Function `email-outbox-send`:
- invoked every minute by `pg_cron` → `pg_net` with the `x-cron-secret`
  header, exactly as `reconcile-funds` (vault `functions_base_url` and
  `cron_secret`), authenticated with `cronAuthorized` before anything else;
- reaches the secret key only through `_shared/core/keys.ts`. It is a
  reviewed system function under Ruling 46, so the `service-role-guard` and
  `secret-scoping` allow-lists gain it explicitly;
- calls `claim_email_outbox(p_limit)` (`service_role` only): `FOR UPDATE
  SKIP LOCKED` on PENDING rows due now, moves them to SENDING, increments
  `attempts`. A SENDING row older than 10 minutes counts as due again;
- renders each template (HTML and text), sends it through Resend with the
  outbox id as the idempotency key, then calls
  `complete_email_outbox(p_id, p_ok boolean)`. Success is SENT. Failure is
  back to PENDING with exponential back-off (1, 5, 15, 60 minutes), and
  FAILED after 5 attempts;
- moves the Resend transport `send-auth-email/resend.ts` to
  `_shared/messaging/resend.ts` and has both functions import it there.
  Same from-address config (`RESEND_FROM`) as the auth emails;
- never logs a recipient address. Sentry events go through the existing
  scrubber.

Retention: the same nightly job deletes SENT and FAILED rows older than
30 days (Claude's call: addresses are not kept longer than needed).

### 5.3 What enqueues what

| Event (in its own transaction) | Template | To |
|---|---|---|
| `open_support_ticket` (non-SYSTEM) | `BUYER_TICKET_OPENED` | `support_ticket_contacts.customer_email` |
| `reply_ticket` (staff) | `BUYER_TICKET_REPLY` | same |
| `update_ticket_status` to RESOLVED or CLOSED, and `close_resolved_support_tickets` | `BUYER_TICKET_STATUS` | same |
| `open_tenant_ticket` | `TENANT_TICKET_OPENED` | `profiles.email` of `opened_by` |
| `reply_tenant_ticket` by TEAFAIR | `TENANT_TICKET_REPLY` | `profiles.email` of `opened_by` |
| `update_tenant_ticket_status` to RESOLVED or CLOSED, and the nightly tenant auto-close | `TENANT_TICKET_STATUS` | `profiles.email` of `opened_by` |

None for SYSTEM tickets (they have no contact), redacted contacts, or a
missing address. An idempotent replay enqueues nothing new, because the
enqueue sits after `idempotency_begin` returns null.

**Redaction.** `redact_ticket_customer_data` also deletes that ticket's
PENDING / SENDING outbox rows and nulls `to_email` on its SENT / FAILED
rows, so the buyer's address leaves the outbox too.

Patch the **latest** definition of each A3 RPC (A5 and later migrations
may have redefined some). The enqueue is added; nothing else in their
behaviour changes.

### 5.4 Email content

- Buyer subject: "New update on your support ticket TK-XXXXXX" (opened:
  "We've received your support request TK-XXXXXX"; status: "Your support
  ticket TK-XXXXXX is resolved / closed").
- Buyer body: the reference, the button link
  `WEB_SUPPORT_TICKET_URL?ref=TK-XXXXXX`, and the line "To read the
  messages, enter the ticket code you were given when you opened the
  ticket." No message text, no secret, no phone number, no order details.
- Tenant body: reference, subject line, category, and "Sign in to the
  Teafair app to read and reply." No link: the Spec B app does not exist
  yet. No message text.

`WEB_SUPPORT_TICKET_URL` goes into `supabase/functions/.env.example`. The
sender fails closed (no send, row stays PENDING, error logged) when a buyer
template is due and the variable is missing.
